# Orbit API — Architecture Guide

A reference for engineers coming from NestJS, Django, or Express backgrounds.

---

## Stack at a Glance

| Concern | Tool |
|---|---|
| Runtime | Bun |
| HTTP Framework | [Hono](https://hono.dev) + `@hono/zod-openapi` |
| Validation | Zod (auto-wired into OpenAPI spec) |
| ORM | [Drizzle ORM](https://orm.drizzle.team) |
| Database | PostgreSQL |
| Auth | Clerk (JWT verification) |
| Logging | Pino via `hono-pino` |
| API Docs | Scalar (auto-generated at `/api-docs`) |

---

## Mental Model: NestJS → Hono

In NestJS you have: **Controller → Service → DB → return response**

In this codebase: **Route definition → Handler → DB → `c.json()`**

The controller and service are collapsed into a single **handler function**. There's no DI container — imports are direct.

| NestJS | Hono equivalent (this codebase) |
|---|---|
| `AppModule` + `main.ts` | `lib/create-app.ts` + `index.ts` |
| `@Controller('/quests')` | `routes/quests/quests.route.ts` |
| DTO class + `ValidationPipe` | Zod schema in `routes/quests/routes.ts` |
| `@Body()`, `@Param()`, `@Query()` | `c.req.valid('json')`, `c.req.valid('param')`, `c.req.valid('query')` |
| `@UseGuards(JwtAuthGuard)` | `resolveUser` middleware applied in `quests.route.ts` |
| `@User()` decorator | `c.var.userId` (set by `resolveUser` middleware) |
| `@InjectRepository()` | Direct `db` import from `db/db.ts` |
| Service method body | Handler function in `*.handlers.ts` |

## The Three Files per Domain

Every domain (quests, saves, lists) has the same three-file structure. Here's what each one does:

### `routes.ts` — The Contract
Defines Zod schemas and OpenAPI route objects. No logic here.
- `insertXxxSchema` — shape of the POST body
- `patchXxxSchema` — shape of the PATCH body (usually `.partial()` of insert)
- `selectXxxSchema` — shape of what gets returned in responses
- `createRoute(...)` — binds method + path + request/response schemas together

This is what auto-generates the Scalar docs at `/api-docs`.

### `*.handlers.ts` — The Logic
This is where business logic lives. Each exported function is one endpoint handler.

```typescript
// The full pattern — everything you need is on `c`
export const createQuest: AppRouteHandler<CreateRoute> = async (c) => {
  const body    = c.req.valid('json');   // validated request body (NestJS: @Body())
  const userId  = c.var.userId;          // from resolveUser middleware (@User())
  const logger  = c.var.logger;          // pino logger

  const [quest] = await db
    .insert(questsTable)
    .values({ ...body, userId })
    .returning();

  return c.json(quest, 201);
};
```

The `AppRouteHandler<CreateRoute>` type is what locks in TypeScript inference — it knows the exact body shape, valid status codes, and response types based on what you defined in `routes.ts`.

### `*.route.ts` — The Wiring
This file creates the router, applies middleware (auth), and binds each route definition to its handler.

```typescript
// quests.route.ts — equivalent to @Controller + @UseGuards
const questsRoute = createAppRouter();
questsRoute.use(resolveUser);  // auth guard on all routes in this file

questsRoute.openapi(list, listQuests);
questsRoute.openapi(create, createQuest);
questsRoute.openapi(getOne, getOneQuest);
// ...

export default questsRoute;
```

## Request Lifecycle (POST /quests)

```
HTTP POST /quests
    │
    ▼
app.ts
  └─ app.route('/', questsRoute)   ← mounts the router
    │
    ▼
quests.route.ts
  └─ questsRoute.use(resolveUser)  ← runs auth middleware first
      • Reads Bearer token from Authorization header
      • Verifies with Clerk SDK → gets clerkUserId
      • Looks up user in DB by clerkUUID
      • Sets c.set('userId', user.id)
      • Calls next()
    │
    ▼
Zod validation (automatic, via @hono/zod-openapi)
  └─ Validates request body against insertQuestSchema
  └─ Returns 422 automatically if invalid — handler never runs
    │
    ▼
quests.handlers.ts → createQuest(c)
  • c.req.valid('json')    → validated body
  • c.var.userId           → authenticated user's DB id
  • db.insert(questsTable) → writes to Postgres
  • if listId provided     → also inserts into list_items
  • return c.json(quest, 201)
    │
    ▼
HTTP 201 { ...quest }
```

## Authentication

`resolveUser` middleware (`middlewares/resolve-user.middleware.ts`) handles auth:

1. Pulls `Authorization: Bearer <token>` from the request header
2. Verifies the token against **Clerk** using `CLERK_SECRET_KEY`
3. Extracts `clerkUserId` (`payload.sub`) from the verified JWT
4. Looks up the internal user in our DB by `clerkUUID`
5. Sets `c.set('userId', user.id)` — our internal UUID, not Clerk's

Every handler downstream reads `c.var.userId`. If the token is invalid or the user doesn't exist in our DB, it returns `401` and the handler never runs.

## Database (Drizzle ORM)

Drizzle is the ORM. Unlike Prisma, there's no separate client — you import `db` and write queries directly with a builder API.

```typescript
// Prisma (what you might know)
const quests = await prisma.quest.findMany({ where: { userId, status: 'active' } });

// Drizzle (what's here)
import { db } from '../../db/db.js';
import { questsTable } from '../../db/schemas/quests.schema.js';
import { and, eq } from 'drizzle-orm';

const quests = await db
  .select()
  .from(questsTable)
  .where(and(eq(questsTable.userId, userId), eq(questsTable.status, 'active')));
```

Schemas live in `db/schemas/`. They define the table structure (columns, indexes, constraints) AND act as the source of truth for TypeScript types. Migrations are generated by Drizzle Kit and live in `db/migrations/`.

## Data Model

```
users (1)
  ├──> quests (many) — cascade delete
  ├──> saves  (many) — cascade delete
  └──> lists  (many) — cascade delete
              └──> list_items (many) — cascade delete
                        ├──> quests (nullable FK)
                        └──> saves  (nullable FK)
                        CHECK: exactly one of questId/saveId must be set
```

**Quests** are the core "task" entity. They unify todos, notes, events, and daily habits under one table — the `type` enum differentiates them. The `isRemembral` flag marks memorable past events (timeline feature). Deletion is always soft — status is set to `"archived"`, the row stays.

**Saves** are bookmarks. When a save is created, metadata (title, thumbnail, author, tags) is scraped from the URL **asynchronously in the background** — the create response returns immediately, and the row is updated once scraping completes.

**Lists** are groupings. A list can contain both quests and saves via the `list_items` junction table. A DB `CHECK` constraint enforces that each row links to exactly one item type.

## Background Scraping (Saves)

When you `POST /saves`, scraping is intentionally fire-and-forget:

```typescript
// saves.handlers.ts
const [save] = await db.insert(savesTable).values({ ... }).returning();

// This runs async — doesn't block the response
scrapeUrl(rest.sourceUrl)
  .then((scraped) => db.update(savesTable).set({ ...scraped }).where(...))
  .catch((err) => logger.warn({ err }, 'background scrape failed'));

return c.json(save, 201); // Returns immediately with partial data
```

This means the first `GET /saves/:id` after creation may return `null` for `title`, `thumbnailUrl`, etc. The scraper (`routes/saves/scraper/`) includes SSRF protection (blocks private IP ranges, validates DNS), sanitization, and platform-specific providers for YouTube, Reddit, and generic OpenGraph.

## Environment Config

`env.ts` validates all environment variables at startup using Zod. If any required variable is missing, the process exits immediately with a clear error — no silent failures at runtime.

Required vars: `DATABASE_URL`, `CLERK_SECRET_KEY`, `LOG_LEVEL`, `VERSION`
Optional vars: `PORT` (default 9999), `FRONTEND_URL` (default `*`), `ANTHROPIC_API_KEY`

## OpenAPI Docs

Interactive docs are auto-generated from the route definitions and available at `/api-docs` (Scalar UI). No manual spec maintenance — the Zod schemas in `routes.ts` files are the source of truth for both runtime validation and the OpenAPI spec.
